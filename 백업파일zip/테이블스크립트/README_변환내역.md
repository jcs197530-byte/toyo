# 토요하자 DB — MySQL → PostgreSQL 16 스키마 변환 결과

## 1. 작업 방식
원본 파일(`토요하자스크립트NEW202608012100.sql`, 4,050줄)은 완성된 스키마 덤프가 아니라
**여러 해에 걸쳐 누적된 운영 변경 이력**(CREATE TABLE, ALTER TABLE, DROP TABLE, RENAME TABLE,
백업/스냅샷 생성, 대량 INSERT/UPDATE/DELETE 데이터 작업이 뒤섞인 로그)이었습니다.

그래서 다음 순서로 처리했습니다.

1. 파일에서 **DDL 문(CREATE/ALTER/DROP/RENAME TABLE, INDEX)만 97개** 추출 (INSERT/UPDATE/DELETE/SELECT/COMMIT 등 데이터 작업은 제외)
2. 각 테이블에 대해 DDL을 **시간 순서대로 재생(replay)** 하여 "최종 컬럼 구성 / PK / 인덱스" 상태를 재구성
   - `CREATE TABLE` → 컬럼 초기화
   - `ALTER TABLE ADD/DROP/MODIFY COLUMN` → 컬럼 반영
   - `ALTER TABLE ADD/DROP INDEX` → 인덱스 반영
   - `RENAME TABLE` → 테이블명 이관
3. 최종 상태를 PostgreSQL 16 문법으로 변환
4. 실제 **PostgreSQL 16을 설치하여 생성 + CRUD 테스트까지 완료**

## 2. 결과물
- `toyohaja_postgresql16_schema.sql` — 최종 테이블 29개 CREATE TABLE + 인덱스 스크립트 (PostgreSQL 16)
- `toyohaja_test_crud.sql` — 실제 테스트에 사용한 검증 스크립트 (참고용)

## 3. 타입 변환 규칙

| MySQL | PostgreSQL 16 | 비고 |
|---|---|---|
| `VARCHAR(n)` | `VARCHAR(n)` | 그대로 |
| `INT`, `INT(n)` | `INTEGER` | display width는 PG에 없음(무시) |
| `INT(n) AUTO_INCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | PG16 표준 identity 컬럼 방식 |
| `DATETIME` | `TIMESTAMP` | |
| `BLOB` | `BYTEA` | |
| `DECIMAL(m,d)` | `NUMERIC(m,d)` | |
| 컬럼명/테이블명 | 소문자로 통일 | PostgreSQL 관례(대문자 사용 시 항상 큰따옴표 필요하므로 회피) |
| `... ADD COLUMN x AFTER y` | `AFTER` 절 제거 | PostgreSQL은 컬럼 순서 지정을 지원하지 않음(항상 맨 뒤에 추가). 실제 저장 순서만 다를 뿐 기능상 영향 없음 |
| `ADD INDEX` | `CREATE INDEX` (테이블 밖에 별도 문장) | |
| `ADD UNIQUE INDEX` | `CREATE UNIQUE INDEX` | |

## 4. 처리 범위에서 제외한 것
- **백업/스냅샷 테이블 5개**는 스키마 생성 대상에서 제외했습니다 (운영 중 임시로 뜬 시점 복사본이라 원본과 동일 구조이며, 재설계 대상이 아니라고 판단):
  `TOYO_STUD_CHUL0526_BACKUP`, `TOYO_TEACHER_CHUL0526_BACKUP`, `TOYO_STUD_INFO0628_BACKUP`,
  `TOYO_STUD_INFO_2017_GRADE`, `TOYO_STUD_FIELD_ATTEND_BAK20161027`
  (필요하시면 소스 테이블과 동일한 구조로 그대로 만들어 드릴 수 있습니다.)
- 개인정보가 담긴 실제 **INSERT/UPDATE 데이터 문장(학생/보호자 정보)** 은 스키마 변환 요청 범위를 벗어나 포함하지 않았습니다.

## 5. 주의가 필요한 부분 (반드시 확인해주세요)

1. **`toyo_stud_info` 테이블의 `parents_no_hp_enc` 컬럼**
   원본 로그 안에서 `CREATE TABLE`/`ALTER TABLE`로 정의된 적이 없는데, 뒷부분 UPDATE 문에서
   `HEX(AES_ENCRYPT(...))` 결과를 넣는 데 사용되고 있었습니다. 즉 **이 스크립트 이력이 시작되기
   전부터 이미 존재하던 컬럼**으로 추정됩니다. `VARCHAR(500)`으로 추정 생성해 두었으니,
   실제 운영 DB에서 `DESCRIBE toyo_stud_info` (MySQL) 결과와 대조해서 정확한 길이를 확인해주세요.

2. **`toyo_stud_info` 테이블 중간의 `DROP TABLE TOYO_STUD_INFO;`**
   로그 3640번째 줄 근처에 이 테이블을 DROP하는 문장이 있지만, 바로 뒤에서도 계속 같은 테이블에
   UPDATE 문이 이어지는 것으로 보아 **실제로 실행되지 않았거나(테스트/스크래치성 기록), 다른 운영
   스크립트와 섞여 들어간 것**으로 판단해 무시하고 마지막 컬럼 상태를 최종 스키마로 채택했습니다.

3. **인덱스명 `stud_score`, `stud_chul` (toyo_stud_info)**
   원본에서 PK가 아닌 일반 인덱스인데 이름이 컬럼명과 겹칩니다(MySQL 관행). PostgreSQL에서도
   문제없이 동작하는 것을 테스트로 확인했습니다.

4. **`toyo_stud_score_hist.seq`를 AUTO_INCREMENT → IDENTITY로 변환**
   기존 PK가 `(seq, gubun, enroll_date, ban, stud_no, subject)` 복합키인데 seq에 identity를
   붙였습니다. 애플리케이션 로직에서 seq를 직접 지정해서 넣는 경우가 있다면
   `INSERT ... OVERRIDING SYSTEM VALUE`가 필요할 수 있습니다.

## 6. 실제 테스트 내역 (PostgreSQL 16.14, Ubuntu 24.04에서 직접 실행)
- 스키마 스크립트 실행 → 29개 테이블 + 인덱스 전부 오류 없이 생성 확인
- INSERT / SELECT / UPDATE / DELETE 정상 동작 확인
- PK 제약 위반 시 `unique_violation` 정상 발생 확인
- UNIQUE INDEX 제약 정상 동작 확인
- ALTER TABLE ADD COLUMN / DROP COLUMN 정상 동작 확인
- BYTEA(구 BLOB) 컬럼 저장/조회 정상 확인
- IDENTITY(구 AUTO_INCREMENT) 컬럼 자동 채번 확인
- DROP TABLE 정상 동작 확인

## 7. 다음 단계 제안
- PHP 애플리케이션 코드에서 MySQL 전용 함수(`AES_ENCRYPT`, `HEX()`, `CURRENT_DATE()`, `FROM DUAL` 등)를
  PostgreSQL 문법(`pgcrypto` 확장의 `pgp_sym_encrypt`, `encode(...,'hex')`, `CURRENT_DATE` 등)으로
  같이 바꿔드릴 수 있습니다.
- 실제 데이터 마이그레이션(MySQL → PostgreSQL 데이터 이관) 스크립트가 필요하시면 말씀해주세요.
