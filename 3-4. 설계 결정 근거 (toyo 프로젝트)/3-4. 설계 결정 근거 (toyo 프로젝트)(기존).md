# 3-4. 설계 결정 근거 (toyo 프로젝트)

| 결정 | 근거 |
|---|---|
| PK를 복합 자연키(`ENROLL_DATE+BAN+STUD_NO`)가 아닌 `id`(surrogate key)로 | 레거시는 날짜+반+학번 조합을 PK로 썼는데, 여러 컬럼을 매번 조인/외래키에 실어야 해 무겁고 관리가 어려움. 대리키로 단순화하고, 중복 방지는 `UniqueConstraint`로 별도 유지 |
| `UNIQUE (student_id, enroll_date)` / `(student_id, enroll_date, subject)` 복합키 | 같은 학생이 같은 날짜에 출석/성적이 중복 등록되는 것을 DB 레벨에서 방지 |
| 출석·성적에 반(class) 스냅샷 컬럼 없음 → `student.class_room`으로만 조회 | 레거시 `TOYO_STUD_CHUL.BAN` 같은 컬럼은 실제로 `TOYO_STUD_INFO.BAN`만 쓰이고 있어 불필요 — 확인 후 제거, 불필요한 비정규화 배제 |
| 학번(`STUD_NO`) 대신 `id` PK로 동명이인 문제 구조적 해소 | 이름·학번 조합이 아니라 FK가 항상 정수 `id`를 참조하므로 동명이인이 있어도 대상이 항상 명확 |
| 세션을 `Session` 별도 테이블로 분리(`TOYO_ID_INFO.TOKEN` 통합 컬럼 대신) | 계정당 다중 기기 로그인·토큰 만료 관리를 위해 1:N 구조 필요, 계정 테이블 비대화 방지 |
| 코드값(`CHUL_KIND` 등)을 범용 코드 테이블(`toyo_code_name`) 대신 Python/DB `Enum`으로 고정 | 실제 값(11=출석, 12=결석, 13=지각, 14=조퇴)이 확정된 닫힌 집합이라, 오타나 존재하지 않는 코드 삽입을 애초에 차단 |
| `varchar(8)` 날짜 문자열 대신 `Date` 타입 | 문자열 정렬/비교 시 발생하는 오류 제거, DB 날짜 연산·인덱스 활용 가능 |
| 비밀번호는 `pwdlib`(Argon2) 해시만 저장 | 레거시 `PASSWD` 컬럼의 약한 해시 방식 대신 현재 권장되는 안전한 해시 알고리즘 적용 |

> `Subject`(성적 과목) enum의 실제 코드값은 아직 확정되지 않아 이 표에는 포함하지 않았습니다.
> 코드값이 확정되면 "코드값을 Enum으로 고정" 행에 함께 반영할 수 있습니다.
